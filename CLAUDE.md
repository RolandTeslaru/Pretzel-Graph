## Project Overview

**PretzelGraph** is a monorepo for a visual agent workflow editor. Users build AI agent pipelines visually using a node-graph canvas. The system compiles those graphs and executes them via a LangGraph-based engine.

## Development Commands

### Frontend (`packages/frontend`)
```bash
npm run dev      # Start Vite dev server
npm run build    # Type-check + bundle
npm run lint     # ESLint
npm run preview  # Preview production build
```

### Backend (`packages/backend`)
```bash
npm run dev    # Start with tsx watch
npm run build  # TypeScript compile
npm start      # Run compiled dist/index.js
```

### Execution Engine (`packages/worker`)
```bash
npm run dev    # Run index + server concurrently (watch mode)
npm run build  # TypeScript compile
npm test       # Jest tests
npm run generate-indexes  # Regenerate barrel index files
```

### Shared Package (`packages/shared`)
No build step — used directly as a workspace dependency.

## Architecture

### Monorepo Layout
```
packages/
  frontend/    # React 19 + Vite + XYFlow graph editor
  backend/     # Express 5 + WebSocket + BullMQ
  shared/      # Domain models (Zod schemas) used by all packages
  vx-ui/       # UI component library (Radix + Tailwind foundations, icons)
  worker/      # Workflow execution engine (LangChain + LangGraph)
```

### Frontend State Management — SDK Pattern
All state lives in Zustand stores wrapped by typed SDK classes in `src/SDKs/`. Each SDK extends `BaseSDK<T_State>` and exposes:
- `useStore` — Zustand store (Immer + Zundo for undo/redo)
- `reducers` — Immer-based state mutations
- `actions` — Side-effectful operations (API calls, etc.)
- `selectors` — Computed/derived values

`SDKManager` is a DI container that wires all SDKs together. The most complex SDK is `WorkbenchSDK`, which owns the entire workflow editor state (nodes, edges, viewport, selection, clipboard, dirty flag).

### Routing
TanStack Router with file-based routes under `src/routes/`. The route tree is auto-generated into `routeTree.gen.ts` — do not edit this file manually.

### Domain Models
All shared types live in `packages/shared/domain/` as Zod schemas with inferred TypeScript types. Key models:
- `Workflow` — Nodes, edges, layout, viewport, cache, validation issues
- `Foundations` — Field, Port, Blueprint base types
- `Vault` — Secrets/credentials
- `Orchestrator` — Execution control messages

Branded string types (e.g., `Workflow.Id`, `Node.Id`) are used throughout for type safety.

### Graph Canvas
`WorkbenchSDK/ui/Canvas/` contains the XYFlow canvas, custom node components, and edge renderers. Nodes are defined by Blueprints; the `FieldRenderer` dynamically renders each node's input fields based on the field's type.

### Execution Engine (`worker`)
- `WorkflowCompiler` — Validates a workflow DAG before execution
- `AggexEngine` — Executes the graph node-by-node; resolves field values and incoming port data
- Node implementations live under `nodes/` organized by provider (Core, OpenAI, Google, Anthropic)
- Uses LangGraph state machines for agent loop execution

### Backend
Express server on port 3001 (configurable via `.env` `BACKEND_PORT`). Routes:
- `/api/library` — Workflow CRUD (Supabase)
- `/api/shelf` — Node blueprint catalog
- `/api/orchestrator` — Trigger workflow execution
- `/api/workbench` — Editor state sync
- WebSocket server for real-time updates (Realtime service)

### Styling
Tailwind CSS 4 with an extensive CSS variable system. Port types have dedicated colors (`--port-message`, `--port-str`, etc.) defined as CSS variables. Dark/light theme is class-based. Custom animations (`neonPulse`, `border-beam`, accordion transitions) are defined in `tailwind.config.ts`.

## Feature Planning Workflow

Ideas and features are managed in a three-stage pipeline:

1. **`FEATURES.md`** — raw idea backlog. Anything goes here, no structure needed.
2. **`SPECS/`** — when a feature is ready to plan, a detailed spec is created here (`SPECS/feature-name.md`) covering motivation, affected files, implementation steps, and open questions.
3. **`TASKS.md`** — actionable tasks broken out from the spec, slotted into the right bucket.

When the user says "let's spec out [feature]", read the relevant codebase and produce a full spec in `SPECS/feature-name.md`, then surface the resulting tasks for `TASKS.md`.

## Conventions

- **Dialogs/Confirmations**: Always use `DialogSDK.actions.push()` with `DialogSDK.Template` or `DialogSDK.AlertTemplate` to open dialogs. Do not use inline `AlertDialog.Root`/`Trigger`/`Content` patterns. See `VaultSDK/ui/VaultPanel.tsx` for examples.

- **Adding a new node**: When creating a new node (`blueprint.ts` + `node.ts` under `packages/worker/src/nodes/`), always also register its blueprint ID in the appropriate drawer in `packages/shared/constants/drawers.ts`. The drawer key should match the node's provider (e.g. `tavily`, `openai`, `anthropic`). For core nodes, use the relevant `CORE_DRAWERS` entry.
